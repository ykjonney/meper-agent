# Personal Agent 产品体验设计

> 状态：**产品体验基线（部分原则已确认，具体交互持续评审）**
>
> 日期：2026-11-27
>
> 本文从用户体验出发描述产品应该如何工作，不定义领域模型、数据库、Runtime、服务边界或其他技术实现。技术设计应在产品体验和功能边界明确后开展。
>
> 本文严格区分：
> - **已确认**：用户明确选择或确认的产品方向。
> - **设计提案**：当前建议采用、仍可评审调整的产品行为。
> - **待决策**：存在多种合理选择，需要后续与用户确认。
> - **暂缓**：不是产品永远不做，而是不作为当前核心体验的前置条件。

## 1. 产品定位

产品以 Personal Agent 体验为核心，同时具备企业环境所需的协作、权限、安全和治理能力。

用户主要通过自然语言与自己的 Personal Agent 交互。Agent 理解用户目标，判断如何处理需求，使用适当能力完成工作，并在过程中持续反馈、允许用户介入，最终交付可检查和继续使用的成果。

产品不是简单的聊天机器人，也不是要求用户手动管理任务、工作流和 Agent 编排的管理平台。

核心体验：

1. 用户自然地提出需求，不必预先选择任务模式。
2. Agent 判断需求性质，决定直接回答、执行普通任务、展示计划或先澄清。
3. 对需要持续推进的工作，Agent 保持目标、计划、进展和成果的连续性。
4. 用户可以随时了解进展、补充要求、调整目标、暂停、恢复、取消或接管。
5. Agent 在用户明确授权的范围内持续监控和执行约定工作。
6. 工作完成后，用户能够检查成果、提出修改并继续之前的工作。

## 2. 已确认的产品体验决策

以下八项为用户已明确确认的方向，是后续产品设计的基线。

| 议题 | 已确认选择 |
|---|---|
| 产品首页 | 混合模式：聊天为主，工作信息作为辅助 |
| 普通任务的工作视图 | 由 Agent 自行判断是否需要展示，用户随时可以展开执行详情 |
| 复杂任务计划的启动 | 根据任务风险和复杂度决定是否需要确认 |
| 对话与工作关系 | 由 Agent 识别工作边界，用户可以调整 |
| 多个工作同时进行 | 对话中展示各自细节，同时提供统一入口查看全局状态 |
| Agent 主动程度 | 在用户授权范围内，可以主动监控和执行约定工作 |
| 专业 Agent 使用方式 | 支持用户主动选择，也支持 Personal Agent 自动调用 |
| 执行过程透明度 | 默认展示关键进展，需要时展开详细执行记录 |

这些选择不意味着所有相关功能都必须在 MVP 一次性实现；具体交付范围仍需通过场景和优先级评审确定。

## 3. 产品设计原则

### 3.1 对话优先，而非对话唯一

自然语言对话是主要入口。用户不需要先学习 Work、Plan、Workflow、Skill 等概念。

但查看全局工作、处理待办、审批操作、浏览成果和管理主动服务，应有直接的产品入口，不必全部依赖聊天命令。

### 3.2 Agent 自主判断交互方式

Agent 根据需求决定直接回答、执行普通任务、制定计划、澄清信息或持续跟进。不得强迫用户为每个需求选择模式。

### 3.3 简单任务保持简单

简单问答和低复杂度任务不应被强制包装成复杂工作管理体验。只有当执行复杂度、持续时间、风险或用户理解需要时，才展示相应详情。

### 3.4 工作连续，但用户始终可控

工作可以跨多轮交互持续推进。用户可以随时了解、调整和接管；Agent 不应把一次对话结束误认为工作完成。

### 3.5 主动行动必须有授权边界

Agent 可以在用户授权范围内主动监控和执行约定工作。授权应明确对象、范围和允许的操作，并允许用户查看、修改、暂停或撤销。

### 3.6 展示可理解、可验证的信息

默认展示对用户有价值的进展、结果、风险和待处理事项；详细执行记录按需展开。不把模型内部推理过程作为产品透明度的替代品。

### 3.7 以交付结果为导向

Agent 不应仅报告“已经完成”。应展示交付内容、完成范围、验证情况、未完成项和必要的后续建议。

## 4. 产品整体信息结构（设计提案）

建议以 Personal Agent 首页和对话为核心，提供以下主要入口：

| 入口 | 用户目的 | 说明 |
|---|---|---|
| 首页 / 对话 | 提出新需求、继续沟通 | 聊天输入是最主要、最显眼的入口 |
| 进行中 | 了解所有正在推进的工作 | 全局视图；可跳转到对应对话和工作详情 |
| 待处理 | 处理需要用户行动的事项 | 包括澄清、审批、确认、验收和异常处理 |
| Projects | 围绕长期项目组织工作 | 提供项目上下文和相关内容入口 |
| Agents | 发现、选择和管理专业 Agent | 支持直接使用和由 Personal Agent 调用 |
| 产物 | 查找、预览和继续使用成果 | 支持按相关工作、对话或项目查找 |

### 4.1 首页内容建议

首页以聊天输入区域为主，辅助展示：
- 正在进行且值得关注的工作；
- 需要用户处理的重要事项；
- 与用户授权目标相关的提醒或建议；
- 最近的对话和工作入口。

首页内容应根据实际状态动态显示。没有待处理事项时不制造空列表；没有重要工作时不以复杂仪表盘填充页面。

以上导航和首页布局属于设计提案，具体信息架构、命名和 MVP 入口待进一步评审。

## 5. 用户提出需求后的体验

Agent 收到输入后，应结合当前对话、项目背景、已有工作和授权范围理解用户意图。用户不必先指定需求属于哪种任务。

### 5.1 需求类型与默认交互

| 用户场景 | Agent 的默认行为 | 用户看到的体验 |
|---|---|---|
| 简单问答 | 直接回答 | 普通对话 |
| 内容生成或轻量处理 | 直接完成必要步骤 | 内容或成果，必要时简要说明 |
| 普通一次性任务 | 自行执行必要步骤 | 简要进展和交付结果 |
| 复杂任务 | 理解目标，必要时澄清，形成计划并执行 | 可查看和调整的计划、进度和成果 |
| 长期任务 | 持续维护目标、进展和未完成事项 | 可持续查看的工作详情 |
| 模糊需求 | 先判断关键缺失信息 | 只询问影响结果的重要问题 |
| 多个需求 | 识别各项需求的边界和依赖 | 同一对话中分别呈现和跟进 |
| 继续已有工作 | 找到相关上下文和成果 | 延续原工作，不要求用户重复描述 |

### 5.2 澄清原则

- 能合理推断且风险较低的信息，Agent 可以明确假设后继续。
- 会显著影响目标、范围、成本、风险或交付结果的信息，应先询问。
- 不影响当前步骤的细节，可以在执行过程中再确定。
- 用户明确授权 Agent 自行判断时，不应重复询问已授权其决定的事项。

### 5.3 多个工作与工作边界

一个对话可以包含多个工作。Agent 负责识别工作边界，用户可以通过自然语言或可视化操作调整。

设计上应支持：
- **拆分**：将一项工作拆为多个独立目标；
- **合并**：将相关工作组织为一个统一目标；
- **关联**：保持工作独立，同时表达前置依赖或关联关系。

这些操作不应成为用户发起每个需求时的必填步骤。只有边界不清晰、影响后续执行，或用户主动调整时才需要显式呈现。

## 6. 计划与执行体验

### 6.1 何时展示计划

简单问答和轻量任务不需要计划界面。复杂任务、长程任务或需要多阶段交付的任务，通常应提供可检查的计划。

计划至少应让用户理解：
- 目标和预期交付；
- 主要步骤和阶段；
- 重要依赖、假设和风险；
- 必要的验收要求。

计划不是一次性静态文档，应能随着需求变化和执行结果更新。

### 6.2 计划确认与操作审批是两件事

是否在开始前确认计划，应根据任务风险和复杂度决定。

建议判断原则：
- 简单、低风险、可逆的工作：直接执行；
- 复杂但目标清晰、风险较低的工作：展示计划，可在适当情况下直接开始；
- 目标存在重大歧义或会显著改变交付结果：先澄清或确认；
- 产生明显外部影响、涉及敏感数据、资金、权限变化或不可逆操作：按授权策略在操作前确认。

用户不必因为计划复杂就确认每个普通步骤；反过来，即使计划已经获准，具体高风险操作仍可能需要单独审批。

### 6.3 计划调整

设计上应支持用户通过自然语言和可视化方式调整计划，例如：
- 增加、删除或修改步骤；
- 改变优先级和执行顺序；
- 修改目标、范围和交付要求；
- 暂缓某一部分，先完成其他部分。

计划调整后，Agent 应说明受影响的后续工作，并保留仍然有效的已完成成果。

## 7. 执行过程的可见性

采用分层展示：

| 层级 | 展示内容 | 默认可见性 |
|---|---|---|
| 关键进展 | 当前在做什么、完成了什么、下一步是什么、是否需要用户行动 | 默认展示 |
| 执行详情 | 步骤状态、工具执行结果、阶段成果、错误和恢复情况 | 用户主动展开 |
| 完整执行记录 | 详细操作记录、工具调用结果、授权和审计信息 | 按需查看，受权限控制 |

执行状态应能区分：
- 正在执行；
- 等待用户输入或确认；
- 等待外部服务或资源；
- 遇到问题并尝试恢复；
- 已暂停；
- 已完成；
- 已取消；
- 部分完成或失败。

进度不能只依赖百分比。Agent 应清楚说明等待原因、失败影响和下一步行动。不得将部分完成伪装成全部完成。

## 8. 用户介入与控制

用户应能在工作过程中通过对话或明确的界面操作：

- 追加要求；
- 修改目标和范围；
- 调整计划；
- 暂停、恢复和取消；
- 对需要审批的操作作出决定；
- 对交付成果提出修改；
- 在适当场景中接管工作，例如直接修改文件或手动完成某个步骤。

### 8.1 追加要求

Agent 判断新增要求是当前工作范围的补充，还是一项独立工作；必要时更新计划，并说明对进度和交付的影响。

### 8.2 修改目标

Agent 应更新后续计划，保留仍有价值的已完成成果，并停止不再需要的步骤。不得在未告知用户的情况下悄悄覆盖原目标。

### 8.3 暂停、恢复和取消

- 暂停：停止后续执行，保留可恢复的工作状态，并说明当前进展。
- 恢复：从可继续的位置推进，必要时先检查外部状态是否已变化。
- 取消：停止后续工作，说明已完成、未完成和已产生的成果。对已经发生的外部操作，不应暗示取消能够自动撤销。

### 8.4 用户接管

用户可能直接修改文件、调整成果或手动执行步骤。Agent 继续工作前应检查相关变化，避免覆盖用户修改，并基于最新状态继续。

### 8.5 待处理入口

建议集中展示需要用户采取行动的事项：
- 需要回答；
- 需要审批；
- 需要确认；
- 需要验收；
- 需要处理的异常。

每个待处理事项应能返回对应对话和工作上下文。

## 9. 异常与恢复体验

| 场景 | Agent 应有的产品行为 |
|---|---|
| 缺少关键信息 | 说明缺少什么，以及为什么需要 |
| 工具或外部服务失败 | 说明失败影响，适当重试或提出替代方案 |
| 权限不足 | 说明需要的权限和用途，请求授权 |
| 用户未及时响应 | 保持等待状态，不擅自执行需要确认的操作 |
| 执行中断 | 告知中断位置、已完成内容和恢复方式 |
| 结果不确定 | 标记不确定性，说明证据和限制 |
| 多个 Agent 结果冲突 | 展示冲突点和依据，必要时请求用户决策 |
| 无法完成 | 明确说明原因、部分成果和可选后续方案 |

异常处理是核心工作体验的一部分，不应只在成功流程设计完成后再补充。

## 10. 成果交付与验收

交付形式至少包括：
- **对话结果**：答案、解释、建议和分析；
- **文件成果**：报告、表格、图片、文档等；
- **可操作成果**：代码项目、网站、数据应用或其他可运行内容。

完成时，Agent 应说明：
1. 目标完成情况；
2. 实际交付内容；
3. 未完成或超出范围的事项；
4. 验证和检查结果；
5. 仍然存在的风险或限制；
6. 可选的后续工作。

用户应能预览、下载、继续编辑或要求修改成果。Agent 应基于已有上下文继续处理验收反馈，而不是要求用户重新发起整个工作。

工作完成状态不能仅由 Agent 自我宣告决定。设计上应结合用户约定的目标、验收要求和可用验证证据；具体完成判定与用户验收规则仍需进一步设计。

## 11. 长期工作与主动服务

主动服务分为三个层次，作为产品能力方向：

### 11.1 持续工作

用户已交代的长程工作可以在用户离开页面或结束当前交互后继续推进，并在用户回来时提供最新状态。

### 11.2 约定式主动服务

用户明确授权 Agent 按周期或条件执行约定工作，例如：
- 每周整理项目进度；
- 监控指定代码仓库的变化；
- 在特定事项到期前提醒；
- 定期生成报告。

### 11.3 主动建议

Agent 根据用户目标、已有工作和授权范围发现潜在问题或机会，向用户提出建议。未经授权，不应将建议自动转化为有外部影响的行动。

### 11.4 主动服务控制

设计上每项主动服务都应让用户了解并控制：
- 服务目标和监控对象；
- 触发条件或执行频率；
- 允许读取和执行的操作范围；
- 哪些操作需要再次询问；
- 通知方式和打扰频率；
- 最近执行记录；
- 暂停、编辑和停止入口。

主动服务不应成为不受控制的后台行为。用户应能知道 Agent 为什么行动、依据什么授权行动，以及如何停止。

## 12. 专业 Agent 体验

专业 Agent 支持两种使用方式：

1. 用户从 Agent 列表主动选择并直接使用；
2. Personal Agent 根据需求，在授权范围内调用专业 Agent。

用户应能理解专业 Agent 参与工作的原因、职责和交付结果。无需默认展示 Agent 之间的全部内部通信和编排细节。

用户可以在需要时指定专业 Agent 参与工作，并要求 Personal Agent 负责协调或检查结果。

## 13. 需要进一步评审的产品问题

以下问题尚未由用户确认。本节是待决策清单，不应被误读为已批准设计。

| 编号 | 待决策问题 | 当前建议 |
|---|---|---|
| D-01 | 对话与工作在界面上如何关联和呈现？ | 工作作为对话中的可识别对象，可展开查看和单独操作 |
| D-02 | 用户如何修改计划？ | 同时支持自然语言调整和可视化编辑 |
| D-03 | 用户离开页面后是否继续执行？ | 已启动且处于授权范围内的工作默认可以继续；高风险动作仍按审批规则处理 |
| D-04 | Personal Agent 自动调用专业 Agent 的授权粒度？ | 支持按 Agent、工作范围或操作类型控制，并展示调用记录 |
| D-05 | 工作完成如何判定？ | 结合目标、验收标准、验证证据和用户反馈，不仅依赖 Agent 自我判断 |
| D-06 | 主动服务如何授权？ | 按服务目标和操作类型分别授权，支持查看、修改、暂停和撤销 |

其他待评审细节包括：
- 首页导航、命名和个性化程度；
- 进行中和待处理列表的排序规则；
- 工作拆分、合并和关联的具体交互；
- 详细执行记录的范围和可见权限；
- 用户接管后如何处理并发修改；
- 主动提醒的频率、渠道和免打扰规则；
- MVP 中语音、移动端和多模态能力的边界。

## 14. 暂缓事项与范围约束

为避免核心体验过早复杂化，当前不把以下内容作为核心体验成立的前提：
- 每种任务形态都设置独立模式和入口；
- 要求用户手动编排复杂任务或 Agent DAG；
- 默认暴露所有工具调用和内部执行细节；
- 简单问答强制创建工作计划；
- 每个工作都必须拥有独立工作台；
- 在核心交互尚未验证前建设复杂 Agent / Skill 市场；
- 过早提供复杂企业管理控制台和多节点执行管理界面。

这些能力并非永久排除。是否进入后续路线图，应基于真实用户场景和产品价值再决定。

## 15. 后续设计顺序

继续以用户旅程和交互场景为主线，先完成产品设计，再推导技术实现。

建议按以下顺序继续：
1. **对话与工作关系**：一个对话如何包含多个工作，用户如何识别、切换、拆分、合并和调整。
2. **工作过程交互**：计划如何展示和编辑，执行如何反馈，暂停、恢复、修改和接管如何操作。
3. **主动服务**：如何创建服务、配置授权、查看执行记录和停止服务。
4. **完整页面与交互规格**：将场景落到页面、状态、操作和异常流程。
5. **产品范围与优先级**：区分 MVP、后续和长期能力，并明确暂不实现不等于产品不做。
6. **技术设计**：在产品行为和边界稳定后，再设计领域模型、Runtime、存储、权限和架构。
