# Agent Flow 1.0.6 交付包安全评估报告
## ——两大关键问题的专业分析

**评估对象**：agent-flow-1.0.6-linux-x86_64.zip 交付包及其生产部署实例（119.119.118.64）
**评估方法**：静态分析（包结构审计、二进制字符串提取、配置基线比对）+ 动态验证（隔离环境攻击复现）
**评估边界**：产品归属方内部授权评估；生产环境仅执行只读检查，全部攻击复现于独立隔离环境（119.119.119.102 实验区，实验后可清理）
**评估日期**：2026-10-23

---

## 问题一：交付包内置出厂默认密钥且生产未强制更换 —— 认证体系与加密体系可被离线击穿

**严重级别**：严重（Critical）
**缺陷类别**：CWE-798（硬编码凭据）、CWE-1188（不安全的默认初始化）

### 1.1 问题描述

交付包内 `env.template` 与启动器兜底逻辑中硬编码了两类安全密钥的出厂默认值：

| 密钥 | 用途 | 出厂默认值 |
|------|------|-----------|
| `JWT_SECRET_KEY` | HS256 会话令牌签名密钥（认证体系信任根） | `dev-only-not-for-production-replace-me` |
| `MODEL_ENCRYPTION_KEY` | 客户录入的第三方模型 API Key 的加密密钥 | 固定值（随包分发） |

经与生产环境 `etc/agent-flow.env` 做等值比对（只输出匹配计数、未导出明文），**两项均维持出厂默认值**。

### 1.2 攻击路径分析

JWT 令牌是**本地可计算凭据**：令牌的有效性完全由持有 `JWT_SECRET_KEY` 者决定。该密钥随交付包分发，即意味着**全部客户（及任何取得交付包的第三方）均持有生产系统的令牌签名能力**。攻击者可离线伪造任意主体（含管理员）的合法令牌，直接穿越认证层，无需口令、无需触碰授权环节。同时 `/docs` 与 `/openapi.json` 在生产对外完全开放（HTTP 200），接口结构、参数模型、错误语义全部自暴露，显著降低攻击者的枚举与利用成本。

`MODEL_ENCRYPTION_KEY` 的影响为**跨客户横向资产泄露**：所有部署共用同一加密密钥，任何获得数据库文件的场景（备份外泄、注入、内部人员）均可离线解密该客户存储的全部第三方模型 API Key。

### 1.3 实证记录

- 生产配置等值校验：`JWT_SECRET_KEY` 与 `MODEL_ENCRYPTION_KEY` 均命中交付默认值（匹配计数 = 1）
- 外网非认证探测：`/docs`、`/openapi.json` 返回 200；业务端点返回 401（认证层本身运作正常——问题不在实现，在密钥管理）

### 1.4 影响（CIA 三元组）

- **机密性**：客户录入的第三方模型 API Key 可被批量离线解密（直接影响计费资产）
- **完整性**：伪造令牌可以任意主体身份执行读写操作，等价于认证体系整体失效
- **可用性**：不构成直接影响

### 1.5 根因

产品缺失安全初始化策略：既未实现"首次启动以 CSPRNG 生成密钥"，也未实现"检测到默认密钥且运行于生产模式时拒绝启动"；交付文档亦未将密钥轮换列为强制步骤。

### 1.6 修复建议

| 时限 | 措施 |
|------|------|
| 立即（运营侧） | 轮换生产 `JWT_SECRET_KEY`（代价仅为全体用户重新登录）；`MODEL_ENCRYPTION_KEY` 不可直接轮换（已有数据无法解密），需供应商提供"旧密钥解密→新密钥重加密"迁移工具后执行 |
| 产品侧（根治） | 首次启动自动生成随机密钥；`APP_ENV=production` 且检测到默认密钥时拒绝启动；交付模板以占位符替代真实值 |
| 边界加固 | 反向代理层关闭生产对外 `/docs`、`/openapi.json` |

## 问题二：授权（License）校验单点化且无完整性保护 —— 机器绑定与 fail-closed 机制可被系统性绕过

**严重级别**：高（High）
**缺陷类别**：CWE-353（缺失完整性校验）、CWE-693（保护机制失效）

### 2.1 机制现状（应予肯定的正面项）

- 授权文件采用 **RSA-2048 签名（PKCS#1 v1.5）+ 载荷加密 + 机器指纹（MAC）绑定**的三层结构，无供应商私钥则伪造授权文件在密码学上不可行
- 未激活状态 **fail-closed 真实生效**（实验①实证）：worker/beat 以 exit code 78 终止并循环重启；`LicenseMiddleware` 对全部业务端点返回 403；前端仅呈现激活向导
- 业务代码 412 个模块全部经 Cython 编译为原生扩展，无字节码可反编译，源码级还原成本极高

### 2.2 漏洞机理

全部授权校验逻辑收敛于**单一模块 `app.core-license`**（`app.core.license`），其余组件——`LicenseMiddleware`（每请求拦截）、`celery_app`（worker 启动校验）、workflow 引擎、`main`——仅调用其导出接口。而 CPython 导入机制**不校验模块文件的真实性**：无哈希锚定、无签名验证、无运行时反篡改检测。因此"执行校验的代码"本身可被任意替换，且所有调用方无从感知。此外，容器模式经环境变量 `AGENT_FLOW_MAC`（源自宿主 `HOST_MAC`）注入机器指纹，license 模块**信任注入值而非实测硬件标识**，构成内建的指纹伪造通道。

### 2.3 攻击实证（隔离环境，两次独立攻击均成功）

**攻击 ②（授权克隆，成本：一条环境变量）**
将生产授权文件原样部署于异构主机 → 返回 `LIC_E_FINGERPRINT`（绑定表层生效）→ 注入 `HOST_MAC=<生产指纹>` 并重建容器 → 返回 `activated:true, LIC_OK`，授权对象、有效期与生产完全一致。**单份授权可在任意数量主机复用，机器绑定失效。**

**攻击 ④（模块替换，成本：约 80 行 Python / 约 30 分钟 / 2 轮接口对齐）**
以 meta_path 导入拦截器（挂载于 `sitecustomize.py`）整体替换 `app.core.license`，在**无授权文件、无指纹注入**条件下：系统返回 `activated:true, code:LIC_OK, expires_at=2099-12-31, days_left=99999`；业务端点由 403（授权拦截）退化为 401（仅认证层），worker 恢复常驻服务。攻击全程未触碰 RSA 体制、未依赖源码、未使用逆向工程产物；接口信息来源为二进制字符串与运行时异常回显（堆栈携带源文件路径与行号，属附带的信息泄露）。

### 2.4 影响

授权体系的**排他性失效**：单份授权可无限克隆部署（攻击②），亦可被通用化补丁永久解锁（攻击④）。供应商在续费、授权合规谈判中失去全部技术约束手段；盗版部署在功能上与正版不可区分。

### 2.5 根因

防篡改维度设计缺位：**单点校验汇聚 + 校验模块无完整性自证 + 指纹信源可注入 + 纯离线无吊销通道**。RSA 体制保护的是"授权数据不可伪造"，而未保护"校验程序不可替换"——攻击者始终选择后者。

### 2.6 修复建议（按优先级）

1. **完整性链**：构建期将 license 模块摘要纳入供应商签名清单；由多个相互独立的模块在启动时及运行期随机抽验其哈希与签名，替换即自曝
2. **去单点化**：关键路径（工作流执行、任务派发、导出等高价值动作）内联独立校验，不信任单一模块返回值
3. **指纹加固**：license 模块直接实测硬件标识，并与注入值交叉核对，注入通道最小化
4. **时间锚点**：数据目录持久化"最后可见时间戳"并纳入签名，检测到时钟大幅回跳即锁定
5. **在线心跳 + 离线宽限期**：建立授权吊销与远期到期强制能力

## 总结论

> 该交付包在**密码学选型与 fail-closed 设计上是合格的**：授权伪造不可行、未激活即拒服。但安全强度被两个工程决策抵消：**安全初始化缺位**（默认密钥随包分发且生产未换，认证信任根等同于公开）与**校验逻辑单点化且无完整性保护**（替换一个模块即整体绕过）。前者为当前生产环境的现实风险（Critical），后者为商业模式风险（High）。两者均有明确、低成本的工程修复路径，建议按上表优先级推进。
